# Serialized Android DeviceSecret initialization

## Problem
On cold first use, independent Android sensing and signing initializers can both
read an absent `rpidSeed`, generate distinct roots, and return a root that a
competing write replaces. A cached TEK then disagrees with the signing identity.

## Goals and scope
All Android initializers in each SDK package share one process-local lock across
the complete read/create/synchronous-persist/return transaction. Native
`BarnardEngine` and `BarnardIdentity` use the same helper. Dart Android and React
Native Android each share that helper implementation between their Controller
and Identity entry points. Multi-process storage arbitration and Swift changes
are out of scope.

## Terminology
DeviceSecret is the stored root. TEK is derived from that root for Scan /
Advertise through the Central / Peripheral GATT Transport. Serialization here
concerns local root initialization, not a change to GATT or Transport messages.

## Behavior
1. Acquire the package's process-local initialization lock.
2. Read `rpidSeed`. Decode existing Base64 with `Base64.DEFAULT`; return existing
   bytes unchanged when their length is at least 32. Malformed Base64 retains
   the existing decode-exception behavior; shorter decoded values are recreated.
3. Otherwise generate 32 random bytes and encode with `Base64.NO_WRAP`.
4. Commit synchronously. Return the generated bytes only after successful commit.
   If commit returns false, throw instead of returning an unpersisted root. The
   lock is released on failure; no automatic retry is introduced.
5. Release the lock. A waiting caller rereads storage and returns the same root.

For example, cold Engine initialization holds the lock while Identity waits;
Engine persists root A and derives its anonymous TEK from A. Identity then reads
A and derives its event signing key from A. Neither path can return a competing
root B. No timeout, background retry, or additional cache is introduced.

## Compatibility, security, and privacy
No public API, schema, storage key, secret size, or Base64 format changes. Existing
installed secrets of at least 32 decoded bytes are reused without rewriting.
No public shape changes. The root remains on-device: no device-unique persistent
identifier is added to on-wire payloads. Mocks are bounded to two callers and
finite waits. Existing examples and protocol payloads remain applicable.

## Validation
Each of the five previously unlocked paths has a concurrent cold-first-use
regression test. A SharedPreferences wrapper snapshots the read and rendezvous
before persistence, so unfixed callers both observe absence. With serialization,
the second caller is observed blocked in the helper before the first is
released; it then reads the persisted value. Both roots must equal storage and
there must be exactly one synchronous commit and no asynchronous apply.
Controller tests also verify their initialized cached TEK uses the returned root.
Cross-path tests exercise sensing versus signing in each package; the native
case constructs a cold Engine concurrently with a cold Identity signing call.

The native SDK CI runs `./gradlew test` on JDK 17. Dart Android CI and the package
README use `./gradlew testDebugUnitTest`. React Native Android currently has no
standalone Gradle settings/wrapper or CI unit-test job; local validation hosts its
unchanged library build in an ignored standalone project with React Android
0.72.0 (the example consumer's version), and runs `:barnard:testDebugUnitTest`.
No Android Kotlin lint or format task is configured in these CI jobs. The Android
mirror guard must remain green. These tests provide JVM unit-test evidence,
not device or multi-process validation.
